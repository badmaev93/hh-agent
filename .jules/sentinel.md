## 2024-11-06 - Path Traversal in Screenshot Debug
**Vulnerability:** A path traversal vulnerability existed in `scripts/search_vacancies.py` where a user-provided search `query` was used to construct the filename for a debug screenshot (`debug_search_{query}.png`) with insufficient sanitization (only spaces were replaced with underscores). A malicious query like `../../../etc/passwd` could lead to writing the screenshot outside the intended `data/` directory.
**Learning:** Even internal tool scripts that dump debug outputs using user-provided strings (like a search query) are susceptible to path traversal. String operations like `replace(' ', '_')` are not enough to prevent directory climbing attacks (`../`).
**Prevention:** Use regular expressions to enforce a strict character allowlist (e.g., alphanumeric and dash `[^\w\-]`) on any user-provided string before incorporating it into a file path.
## 2024-11-06 - Prevent Playwright SSRF / Arbitrary Local File Access
**Vulnerability:** URLs passed to `page.goto()` were not validated. If an attacker controlled these URLs, they could trigger arbitrary local file access (via `file://` scheme) or Server-Side Request Forgery (SSRF) vulnerabilities.
**Learning:** Browser automation tools like Playwright can act as powerful vectors for SSRF and local file inclusion if navigation URLs are not strictly controlled, since they inherently trust standard browser schemes.
**Prevention:** Implement strict allowlisting of URL schemes (e.g. `http://`, `https://`) before passing any untrusted URL to navigation functions.
## 2024-11-06 - Incomplete SSRF Prevention via Domain Restriction
**Vulnerability:** While Playwright URL validation ensured only `http://` and `https://` schemes were used (preventing `file://` or `javascript:` access), it did not restrict the destination domain. A malicious user-provided URL could direct the agent's Playwright browser to an arbitrary external server or an internal service (e.g. `http://localhost:8080`), leading to Server-Side Request Forgery (SSRF) and data exfiltration.
**Learning:** Checking URL schemes alone is insufficient for browser-based automation tools. Because Playwright navigates to whatever valid HTTP/HTTPS URL it is given, attackers can use the agent as a proxy to attack internal network resources or phish for sensitive data.
**Prevention:** In addition to strict scheme allowlisting, validate the parsed URL's hostname to ensure it strictly matches the expected target domains (e.g., `hh.ru` or `.hh.ru` subdomains) before passing the URL to `page.goto()`.
## 2025-02-14 - SSRF Bypass via URL Parsing Inconsistencies (Playwright vs. Python urlparse)
**Vulnerability:** The `is_safe_url` function relied on Python's `urllib.parse` to validate the hostname of a URL before passing it to Playwright for navigation. However, browsers (and by extension Playwright) parse URLs differently than Python's `urlparse`. A malicious user could craft a URL like `http://evil.com\@hh.ru` (or use URL encoding or whitespace/control characters) which Python interprets as having the host `hh.ru`, but Playwright navigates to `evil.com`.
**Learning:** Security validations must account for parser differentials. When an input is validated by one system (Python `urllib.parse`) but consumed by another (a web browser engine via Playwright), discrepancies in parsing logic can lead to critical bypasses (SSRF, XSS, etc.).
**Prevention:** Before parsing URLs in Python, normalize them to match browser behavior (e.g., replace `\` with `/`, remove whitespace and control characters, URL decode). Additionally, reject features that commonly cause discrepancies and are unnecessary for the application (like basic auth via `@` in the URL).
